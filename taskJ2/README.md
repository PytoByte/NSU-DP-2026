# taskJ2 — синхронизированный доступ к списку

Многопоточное приложение на Java: **родительская нить** читает строки и кладёт их
в начало связного списка, а **дочерние нити** (их число настраивается) параллельно
сортируют этот список «бесконечным пузырьком». Состояние списка можно в любой
момент напечатать, и оно всегда согласовано. Есть две реализации списка —
собственная (поузловые блокировки) и библиотечная
(`Collections.synchronizedList(new ArrayList<>())`); для обеих измеряется число
шагов сортировки.

## Как это работает

1. Главный поток читает строки из `System.in`. Строки длиннее `maxLineLength`
   (по умолчанию 80) режутся на части, каждая часть кладётся **в начало** списка
   (`addFirst`).
2. **Пустая строка** — команда «показать список»: текущее (возможно, частично
   отсортированное) состояние печатается обычным циклом `for-each`.
3. Параллельно `N` дочерних нитей выполняют бесконечный пузырёк: нить раз за
   разом проходит весь список от головы к хвосту и на каждой паре соседей делает
   «шаг» — попытку поменять их местами (при необходимости переставляя ссылки).
4. Между шагами и внутри шага выдерживается настраиваемая задержка, поэтому
   пользователь во время паузы видит актуальное состояние списка.
5. Конец ввода (`Ctrl+D` / `Ctrl+Z`) завершает программу; в конце печатается
   суммарное число шагов всех нитей.

> Требования: JDK 17+ и Gradle (через wrapper). Сборка проверялась на JDK 21.
> На JDK 26 Gradle 8.14 не компилирует build-скрипт — запускайте сборку на JDK
> 21/23/24 (`JAVA_HOME` указывает на нужный JDK).

## Запуск

```powershell
# интерактивный режим (свой список, 3 нити, задержка 1 c между шагами)
./gradlew run --args="--type=linked --threads=3 --between=1000"

# библиотечный список
./gradlew run --args="--type=library --threads=3 --between=1000"

# замер: 50 записей, нити останавливаются после полной сортировки
java -cp build/classes/java/main org.example.app.Main --type=linked --threads=3 --between=0 --benchmark=50
```

Аргументы командной строки:

| аргумент | смысл | по умолчанию |
|---|---|---|
| `--type=linked\|library` | реализация списка | `linked` |
| `--threads=N` | число дочерних нитей | `3` |
| `--between=MS` | задержка между шагами | `1000` |
| `--inside=MS` | задержка внутри шага | `0` |
| `--max-line=N` | порог резки строки | `80` |
| `--benchmark=N` | headless-замер на N записях | — |
| `--duration=MS` | длительность окна замера (иначе — до полной сортировки) | — |

## Структура классов

Пакеты: `common` (инфраструктура, не зависит от реализации списка), `list`
(список и его сортировка), `app` (приложение и ввод/вывод).

### `org.example.common`

* **`ListType`** (`enum`) — выбор реализации списка: `LINKED` (своя) или
  `LIBRARY` (библиотечная); умеет разбирать строку аргумента.
* **`AppConfig`** (`record`) — вся конфигурация запуска в одном объекте
  (тип списка, число нитей, задержки, порог строки, параметры замера),
  а также значения по умолчанию и признак режима замера.
* **`DelayConfig`** (`record`) — регулируемые задержки: `betweenStepsMillis`
  (между шагами) и `insideStepMillis` (внутри шага); выполняет сам `sleep`.
* **`StepCounter`** — потокобезопасный счётчик шагов и перестановок; разделяется
  всеми дочерними нитями и нужен для отчёта.
* **`BubbleSorter`** — контракт дочерней нити-сортировщика (`Runnable` + `stop`).
* **`AbstractBubbleSorter`** — общий «двигатель» бесконечного пузырька: крутит
  проходы, пока нить не остановлена; конкретный обход задаёт подкласс.

### `org.example.list`

* **`SyncStringList`** — контракт потокобезопасного списка строк: вставка в
  начало, размер и `Iterable` для вывода через `for-each`.
* **`Node`** (`package-private`) — узел двусвязного списка: неизменяемое значение,
  ссылки `prev`/`next` и собственный `ReentrantLock`.
* **`LockingLinkedList`** — собственная реализация: двусвязный список с поузловыми
  блокировками, перестановкой ссылок и согласованным снимком для итератора.
* **`LinkedListBubbleSorter`** — бесконечный пузырёк по связному списку (обход по
  ссылкам, своп через `LockingLinkedList.swapAdjacent`).
* **`SynchronizedArrayList`** — библиотечная реализация:
  `Collections.synchronizedList(new ArrayList<>())`; вставка `add(0, v)`, своп
  `Collections.swap`, сравнение и своп — под монитором списка.
* **`ArrayListBubbleSorter`** — адаптированный пузырёк по индексам поверх
  `SynchronizedArrayList`, с сохранением задержек.

### `org.example.app`

* **`Main`** — точка входа: разбирает аргументы, собирает список и нити, в
  интерактивном режиме читает ввод главным потоком, в конце печатает метрики.
* **`InputReader`** — цикл чтения строк в родительской нити: режет длинные строки
  и кладёт части в начало списка; пустая строка печатает список.
* **`ListPrinter`** — печать состояния списка стандартным `for-each`.
* **`BenchmarkRunner`** — headless-прогон для воспроизводимого замера числа шагов.
* **`SorterRunner`** — вспомогательные операции запуска и остановки дочерних нитей.

## Контракты ключевых методов

* `SyncStringList.addFirst(String)` — атомарно вставляет значение в начало списка.
* `SyncStringList.size()` — текущее количество записей (снимок).
* `SyncStringList.iterator()` — согласованный снимок значений; безопасен при
  параллельных перестановках, пригоден для `for-each`.
* `LockingLinkedList.swapAdjacent(Node a, Node b)` — переставляет соседние узлы
  `a`, `b` (`b == a.next`), переустанавливая ссылки; возвращает `true`, если
  перестановка выполнена, и `false`, если пару уже изменил другой поток.
* `SynchronizedArrayList.compareAndSwap(int i)` — под монитором списка сравнивает
  элементы `i` и `i+1` и при необходимости меняет их местами через
  `Collections.swap`; возвращает факт перестановки.
* `AbstractBubbleSorter.onePass()` — один полный проход по списку; возвращает
  `true`, если в проходе была хотя бы одна перестановка (используется в режиме
  замера «до полной сортировки»).
* `StepCounter.recordAttempt()` / `recordSwap()` — зафиксировать шаг / реальную
  перестановку.

## Синхронизация и инварианты

* **Нет блокировки всего списка на время сортировки.** Используются только
  поузловые блокировки (`Node.lock`); в библиотечной версии — монитор
  `synchronizedList` на одну операцию, не на весь проход.
* **Порядок захвата — строго «от головы к хвосту».** Своп соседней пары
  захватывает пару вместе с её соседями именно в этом порядке; вставка в начало
  захватывает новый узел (он ближе к голове) раньше старой головы. Это исключает
  взаимные блокировки.
* **Защита от дедлока.** Порядок берётся из прочитанных ссылок и при гонке может
  оказаться несогласованным (сосед успел уехать), поэтому узлы захватываются
  `tryLock` с таймаутом: при неудаче захваченное освобождается и попытка
  повторяется — вечного ожидания не возникает.
* **Ревалидация после захвата.** Если за время захвата пара перестала быть
  соседней (`a.next != b`) или у неё сменились соседи, перестановка пропускается
  или повторяется; это же исключает «пинг-понг» двух потоков на одной паре.
* **Своп — только ссылки.** Значение узла неизменяемо (`final value`); меняются
  исключительно `prev`/`next`, содержимое строк между записями не переставляется.
* **Согласованный снимок.** `iterator()` сначала копирует значения под короткими
  поузловыми локами (без I/O под локом) и сверяет длину с `size()`, поэтому в
  выводе всегда ровно ранее введённые строки.

## Две реализации: в чём разница

| | `LockingLinkedList` | `SynchronizedArrayList` |
|---|---|---|
| структура | свой двусвязный список | `ArrayList` в обёртке `synchronizedList` |
| вставка в начало | O(1) | O(n) (`add(0, v)`) |
| своп | переустановка ссылок, поузловые локи | `Collections.swap`, монитор списка |
| параллелизм | нити работают на разных парах | операции сериализуются монитором |
| индексы | нет (только ссылки) | «плывут» из-за вставки в голову |

## Теоретический расчёт числа шагов

Обозначения: `n` — число записей, `k` — число дочерних нитей,
`Δ = inside + between` — задержка на шаг (плюс накладные расходы).

1. **Один поток.** Пузырёк делает по `n-1` сравнений за проход; число проходов до
   полного порядка `P ≤ n-1`. Значит `steps(1) = P·(n-1) ≤ (n-1)²`.
2. **`k` потоков.** Все нити выполняют одни и те же детерминированные проходы, то
   есть дублируют работу: список упорядочивается примерно в `k` раз быстрее, и
   каждая нить успевает ≈ `1/k` от одиночного числа проходов. Поэтому

   `steps(k) ≈ P·(n-1) + O(k·retries)`,

   где `retries` — повторные попытки/пропущенные пары при конкуренции. То есть
   суммарное число шагов растёт с `k` слабо, а не пропорционально `k`.
3. **Задержки.** Если задержка доминирует, за окно `D` каждая нить делает
   ≈ `D/Δ` шагов, а суммарно `steps(k, D) ≈ k·D/Δ` — различие реализаций
   исчезает, время уходит в `sleep`, а не в работу с памятью.

## Измерения

Замер headless: `--benchmark=N` (без `--duration` нити останавливаются, когда
полный проход не потребовал ни одной перестановки). Данные детерминированы
(seed 42), `n = 50`.

**До полной сортировки, без задержек:**

| нитей | `linked`, шагов | `library`, шагов | перестановок |
|---|---:|---:|---:|
| 1 | 2254 | 2254 | 666 |
| 2 | ~2362 | ~2313 | 666 |
| 3 | ~2425 | ~2401 | 666 |
| 4 | ~2670 | ~2499 | 666 |

**Фиксированное окно 2 с, задержка 1 мс** (`--duration=2000`): ≈ 1127 шагов на
нить у обеих реализаций (≈ `k·D/Δ`), отличие в пределах шума.

### Объяснение

* **666 перестановок** во всех прогонах — это число инверсий набора; каждая
  перестановка обязательна, поэтому от числа нитей оно не зависит.
* **2254 шага** у одного потока = `P·(n-1) = 46·49`; связная и библиотечная
  версии совпадают, потому что алгоритм один и тот же.
* **С ростом числа нитей** суммарные шаги растут слабо: нити дублируют одни и те
  же проходы и сортируют список «вместе», а лишние шаги — это повторные проверки
  и пропущенные пары при конкуренции. Библиотечная версия даёт чуть больше
  холостых шагов из-за сериализации на мониторе списка и «плавающих» индексов.
* **С задержками** число шагов за окно линейно растёт по `k` у обеих реализаций
  (`k·D/Δ`): узкое место — `sleep`, а не синхронизация.
